- Status: **Approved** by the owner on 2026-10-19 (revision 2, independently reviewed by requirements, security, UI/UX and operations agents). **Revision 3** (2026-10-19) folds in the decisions of the owner interviews and the consistency notes C1 to C33 of PRD-0003, PRD-0004 and PRD-0005 (section 12); it is editorial and consequential, no goal changes; the owner confirms it with the merge of its pull request. Items marked "proposed" were confirmed or closed by the skeleton PRD.
- Owner: Benjamin Honauer
- Date: 2026-10-19
- Related ADRs: 0001-0012 (0010 and 0011 are proposed, 0012 is accepted)
- Related: PRD-0002 and `docs/spikes/2026-shell-spike-report.md`; PRD-0003 (walking skeleton), PRD-0004 (platform capabilities), PRD-0005 (visual language)

## 1. Problem and goals
Departments need many internal tools and automations. Building each as a standalone app duplicates login, permissions, look and operations. slg-os provides one platform with an OS-like desktop in the browser, single sign-on against the local Active Directory, and a mandatory contract that lets independent teams add modules quickly and consistently.

Goals:
- G1: A window-based desktop shell where users open permitted modules in windows.
- G2: Authentication against AD via Keycloak (ADR-0001).
- G3: Group-based authorization managed in an admin UI (ADR-0006).
- G4: A versioned module contract so a new module can be registered without changing the core (ADR-0002, ADR-0005).
- G5: Consistent UI/UX, bilingual (de/en) via i18n, WCAG 2.2 AA, across the shell and all modules.
- G6: Operable by a small team on a single server (ADR-0009).

## 2. Non-goals
- High availability, Kubernetes, multi-site deployment.
- Modules from outside the platform team's review process (ADR-0007).
- Mandatory collection of business-level audit data (ADR-0008).
- Any concrete business module (each gets its own PRD in its own repository).
- Languages beyond German and English (the design must not preclude them).

## 3. Users and roles
- End user: signs in, opens permitted modules, sets language/theme.
- Module developer (internal team): builds a module from the template and the SDK.
- Platform administrator (`platform-admin`): registers modules, maps AD groups to roles/permissions, revokes sessions. Seeded through a configured AD group (FR-5a).
- Auditor: read-only access to the security audit log. Not part of phase 1 (Q14); platform administrators read the log and each read is audited.

## 4. Functional requirements
Each requirement is testable; "AC" are acceptance criteria.

### FR-1 Sign-in and sign-out
Unauthenticated users are redirected to Keycloak; after login the desktop appears. Sign-out ends the session in shell and modules. The core is a backend-for-frontend (ADR-0012): the browser holds only a session cookie, never a token.
- AC1: The core is a confidential OIDC client using the authorization code flow with PKCE (S256); implicit and password grants are disabled (see 8.1).
- AC2: Sign-out uses RP-initiated logout; Keycloak back-channel logout invalidates the server-side session at once, so no further module request is forwarded (see 8.2).

### FR-2 Desktop shell
Windows (open, move, resize, minimize, maximize, close, focus), the open-window list in the top bar, launcher listing only modules the user may use, desktop icons, notification area, per-user persisted layout and preferences. Behaviour is specified in section 6.
- AC1: The launcher shows exactly the enabled modules for which the user holds at least one permission; a user with no mapped group sees an empty launcher with an explanatory message.
- AC2: Persisted layout entries referring to disabled, removed or no longer permitted modules are skipped without error and with a notice; entries of merely disabled modules are retained.

### FR-3 Language and theme
German/English and light/dark switchable per user; all shell texts come from i18n resources.
- AC1: Switching language or theme updates shell and all open windows without reload and without losing module state (UI-22, UI-25).
- AC2: A missing translation key in either language fails CI (UI-26).

### FR-4 Module registry
Administrators register a module by submitting its manifest through the admin UI or admin API (same validation). Registration is an admin-only action; modules do not self-register (Q16).
- Manifest fields: `id` (unique, immutable, `[a-z][a-z0-9-]{2,31}`), `name`, `version` (SemVer), `contractVersion` (range), `icon`, i18n resource paths for de and en, `entryPoints` (federated remote URL, API base path, health URL; each with `instanceMode` `singleton|multiInstance`, `minWindowSize`, `minViewport`, `category`), `permissions[]` (names `<moduleId>.<resource>.<action>` with de/en labels), optional `suggestedRoles[]`, `requires` (React range, design-system range, per ADR-0005 and ADR-0010) and `closeGuard` support. Integrity hashes are computed by the core at registration for every JavaScript file of the build and are never supplied by the module (8.3). Each entry point may also declare `timeoutSeconds` (default 10, max 300), `maxBodyMB` (default 10, max 100), `streaming` (`none|sse`) and its error codes (UI-30); the module lists the caller modules allowed to call it (8.4). On the first manifest submission, and before the module container is first started, the provisioner (a separate container, PRD-0004 PF-4) idempotently provisions the module's database schema and role, its Keycloak audience, scope and service-account client, and the credential files (audited).
- AC1: A manifest with a missing or unknown field, duplicate id, incomplete language, invalid permission name, unsupported contract version, or oversize payload (> 256 KB) is rejected; the response lists every violation with field path and message (de/en).
- AC2: Registering a higher `version` of an existing id stores it as `registered`; it becomes active only through an explicit activation after pre-flight checks (PRD-0004 PF-5 AC4); the previous manifest is kept and one admin action rolls back to it. Order: an upgrade deploys the backend container first (backward-compatible API) and then registers the new remote; a rollback runs in reverse; the admin UI shows both versions and warns on a mismatch.
- AC3: An upgrade that removes or renames a permission, or raises the required contract major, is rejected unless flagged `breaking`; breaking upgrades list affected mappings and need explicit confirmation. Mappings of removed permissions are marked orphaned, never silently deleted. The per-entry fields `timeoutSeconds`, `maxBodyMB` and `streaming` are validated by the manifest schema (PRD-0003 SK-7 AC1) and enforced by the gateway (SK-5 AC3).
- AC4: Every registration, upgrade, rollback, disable, enable and deletion creates an audit entry.
- AC5: Server-side fetches of manifest-referenced URLs obey the SSRF rules in 8.6.
- AC6: A manifest whose `requires` is not satisfied by the React and design-system versions the shell provides is rejected with a clear message. This check is mandatory; the Module Federation runtime version check is not a control (it fails closed or open depending on load order, ADR-0010).
- AC7: Registration copies the build into an immutable, content-addressed store. It rejects symlinks and hard links, restricts file types, hashes all files, re-verifies an existing store directory, makes the store read-only, switches the active version atomically and validates the entry path on the server. Changing the module container's build after registration does not change what is served. Details: the build source is a build archive or an HTTP file listing (`build-manifest.json` with paths and sizes) fetched under 8.6, never the live container directory; unpacking enforces limits on archive size, file count and path length, rejects `..` and absolute paths and HTML files; each file is served with a fixed type from an allowlist plus `X-Content-Type-Options: nosniff`; every path not in the registry snapshot answers 404; files are served by the proxy only after an `auth_request` check against the core that requires a valid session and a permission of the module (otherwise 404, no leak of module existence; the subrequest fails closed; the import map in the shell document lists only modules the user may use; PRD-0003 SK-8 AC3). The store layout is `/var/slg/store/<moduleId>/<version>-<treeSha256>/`, written to a temporary directory, verified and renamed; the active version is a database field, not a symlink. The shell document always references versioned paths; the three previous versions and every version younger than the absolute session lifetime (10 h) stay served; older ones are removed by an audited admin job; the store volume is monitored (alert at 70 %). The core refuses to activate a module whose store directory fails verification.

### FR-4a Module disable/enable
- AC1: A disabled module is absent from every launcher, its API routes return 503 with a machine-readable code, the gateway forwards no requests for it and cached module tokens are dropped.
- AC2: Windows open at disable time show the "module disabled" state within the health interval of FR-10 (15 s, at most 45 s after three failed checks).
- AC3: Mappings and user layouts are retained; enabling restores access without re-mapping.

### FR-5 Permission model
- Effective permissions are the union of the permissions of all roles mapped to the user's AD groups (identified by Keycloak group claim, full path). No explicit deny; absence means deny. Roles are platform-owned bundles of permissions; manifests only suggest them.
- AC1: A user with no mapped group gets 403 from every module API.
- AC2: A removed mapping applies from the next request after the permission cache expires (<= 60 s). For a changed AD group the worst case is about 16 minutes (LDAP sync 10 min, token renewal 5 min, cache 1 min), slightly above the 15 minutes of Q7; a 9-minute sync interval restores the strict bound if wanted; module access tokens issued by the gateway live at most 5 min. A "revoke sessions" action (user or all) is available and audited.
- AC3: The backend SDK enforces permissions by annotation and filter; an integration test proves 403 without the permission regardless of UI state. The frontend SDK offers an equivalent check for hiding UI only.
- AC4: The core resolves effective permissions server-side. Groups come from the ID token and are kept in the server-side session, refreshed with every token renewal; the SDK reads a module's permissions through the internal core API `GET /core/internal/api/v1/permissions?sub=` with a short cache (<= 60 s); the endpoint has no route from the public proxy, requires a service-account token of a registered module and returns only that module's own permissions (`<moduleId>.*`), rate-limited (PRD-0003 SK-3 AC7, SK-6 AC4). A user without a live session has no permissions in this lookup; background work on behalf of such users is Q35. Modules never see this mechanism (Q12).

### FR-5a First-admin bootstrap
- `SLG_BOOTSTRAP_ADMIN_GROUP` names an AD group. It seeds the `platform-admin` mapping when the database holds no admin mapping; afterwards admin rights come from stored mappings.
- AC1: With an empty database and the variable unset the core refuses to start.
- AC2: The last admin mapping cannot be deleted through the UI or API.
- AC3: Lock-out recovery: delete the admin mapping in the database (documented), set the variable, restart. A break-glass local Keycloak admin exists; its use is alerted and audited.
- AC4: Bootstrap seeding and break-glass use are audited.

### FR-6 Module SDK
Backend library (Spring) and frontend package. Only Spring and React modules are supported by the contract.
- Backend: token validation (issuer, per-module audience, signature, expiry, `azp`), permission checks, identity access, service-account client for module-to-module calls, logging with correlation ID, health endpoints.
- Frontend: identity (profile only; no token is ever available to JavaScript, ADR-0012), permission hook, `useTranslation`, locale formatters, theme and language hooks, state components (Loading, Empty, Error, Forbidden, NotFound, Offline, SessionExpired), close guard, live-region announce API, window integration. The frontend SDK provides the only HTTP client: it adds the CSRF header and `X-Correlation-Id` and maps gateway error codes (FR-11); raw `fetch` calls fail the CSRF check.
- AC1: SDK-provided context values and callbacks have stable identity (an unstable callback caused a render storm in the spike); a render-count test is part of the contract test.
- AC2: The SDK version is tied to the contract version. Only the current contract major is supported (Q13): registration rejects manifests for any other major, and a platform upgrade that raises the major is rolled out together with updated modules (see 10).

### FR-7 Module template
A template repository produces a compliant module that builds, tests (80 % gate), containerizes, validates its manifest, and can be registered by an administrator via FR-4.
- AC1: A module generated from the template passes `docs/reviews/module-registration-checklist.md` without edits.
- AC2: The template contains an `index.html` entry (also its standalone dev harness), `dts: false` for the federation plugin (otherwise the DTS worker crashes the dev server), the shared entries including the `react/` and `react-dom/` prefixes, and the `base` path `/modules/<id>/remote/`; a contract test builds it from a clean checkout.

### FR-8 Failure isolation
- AC1: A remote-entry load failure or runtime exception shows an error boundary with Retry and "Copy details" in that window only; shell and other windows stay operable (E2E test with a stopped module container).
- AC2: Module API calls are subject to the gateway timeout (FR-11 AC6; default 10 s); errors map to a standard problem-details body with a machine-readable `code` and the correlation ID.
- AC3: The registry and admin UI remain usable while any module is down.

### FR-9 Security audit log
Events: login, failed login (ingested by polling the Keycloak events API with read-only service accounts, PRD-0004 PF-2), logout, session revoke, mapping change, admin-role change, module register/upgrade/rollback/disable/enable/delete, bootstrap use, break-glass use, reads of the audit log, session termination by a security control (refresh-token reuse, administrative revoke, vault failure; no token content). Session expiry and refresh failures are logged as logout; ADR-0008 scope is unchanged. Service-account events and repeated 403s are not audited by the core (Q17, ADR-0008 unchanged). Fields: timestamp, event type, actor id, source IP, object, outcome, correlation ID and a `detail` field (ids and permission names only, hashed into the chain). No request bodies or business data.
- AC1: Each event produces exactly one entry, verified by integration test.
- AC2: UPDATE/DELETE on the table by the application DB role fails; a daily hash-chain verification detects a modified row.

### FR-10 Health and diagnostics
Platform and per-module health/readiness; administrators get an operational overview.
- AC1: The core polls module readiness every 15 s (modules send no heartbeat); three consecutive failures mark a module DOWN. A DOWN module disappears from the launcher but stays in the registry; the gateway answers calls to it with 503 `MODULE_DOWN` without forwarding.

### FR-11 Gateway and session (backend-for-frontend)
All browser calls to the core and to module backends go through the core gateway on the shell origin (ADR-0012). The gateway routes `/modules/<id>/api`; the proxy serves static files (the shell assets and, after an `auth_request` check, the module remote files) and never forwards API calls.
- AC1: Login: the pre-login state (OIDC `state`, `nonce`, PKCE verifier) lives in a separate `SameSite=Lax` cookie valid for 10 minutes. The callback response issues a fresh session id (no fixation). The session cookie is `__Host-slg-session` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, no `Domain`) with a 128-bit random id stored only as a hash. The callback answers with a 200 interstitial that navigates on (a redirect chain started at another site would not carry the `SameSite=Strict` cookie); if a supported browser fails this, the cookie falls back to `SameSite=Lax` (still `__Host-`). `Lax` also sends the cookie on cross-site top-level GET navigations, which is acceptable only because GET never changes state and every state-changing request needs the custom header and the `Origin` check; the CSRF tests run against both variants (PRD-0003 SK-3 AC3, Q37, ADR-0015). The interstitial navigates to the validated relative path (attribute-encoded) and carries no inline script. After login the return target must be a relative path matching `/app/<moduleId>/...`; anything else becomes `/`. Idle timeout 30 min (only user-initiated requests count, not polling marked `X-Slg-Background`), absolute session 10 h; Keycloak SSO and refresh-token lifetimes are at least that long.
- AC2: CSRF: every state-changing request needs the custom header and an `Origin` equal to the shell origin; a missing `Origin` on a non-GET request is rejected; GET requests never change state; logout is `POST` only. Server-sent-event GET requests need a valid session and, where the browser sends `Origin` or `Sec-Fetch-Site`, a same-origin value (no ticket: WebSocket is out of phase 1 and `EventSource` cannot send the CSRF header); they are read-only, a module endpoint that changes state on GET fails registration review, and the stream is authorised per connection and closes at session end. Covered by tests.
- AC3: The gateway obtains an audience-bound access token per module (refresh-token down-scoping, or token exchange for the confidential client if production Keycloak supports it, Q26), forwards it, and caches it per session and module until expiry; the cache is dropped on module disable, session revoke, mapping change and logout. Forwarded tokens carry identity (`sub`) but no group list; groups stay in the server-side session. Module-scoped tokens are held in memory only.
- AC4: Errors: an expired or revoked session yields HTTP 401 with code `SESSION_EXPIRED` (shows UI-13); a module's own 401/403 passes through with a different code and never triggers UI-13. If Keycloak is unreachable during a refresh the gateway keeps the session and answers 401 `AUTH_UNAVAILABLE` once the cached module token has expired (at most 5 min), without showing SessionExpired. If a refresh response is lost or refused, the session is terminated. Streams are closed when the session ends or the token cannot be renewed.
- AC5: Refresh tokens are encrypted at rest (AES-256-GCM, key from a secret file with a key id for rotation) in the session store, which is excluded from backups; after a restore all sessions are invalid. Refresh is serialised with a row lock and attempted 60 s before expiry; last access is written at most once per minute; expired sessions are purged hourly.
- AC6: The gateway streams request and response bodies without buffering and passes SSE; WebSocket is not supported in phase 1. Per-entry-point overrides come from the manifest (`timeoutSeconds`, `maxBodyMB`); idle streams close after 60 s without data. The implementation uses a non-blocking client or virtual threads (fixed in the skeleton ADR).
- AC7: The gateway forwards a request to `/modules/<id>/api` only if the module is enabled and the user holds at least one permission of that module. Core administration APIs require the corresponding admin permission and, for mapping changes, registration and revoke-all, a re-authentication not older than 5 minutes (`max_age`).
- AC8: The session store is PostgreSQL (proposed, to be confirmed in the skeleton ADR, Q28). If it is unavailable the gateway answers 503 `SESSION_STORE_DOWN`, with no fallback to unauthenticated or in-memory sessions. A DOWN module yields 503 `MODULE_DOWN`, counted per module.
- AC9: Timeouts, correlation ids (a new id per inbound request; inbound values are accepted only from the proxy) and problem-details errors follow FR-8; the gateway adds no business logic.

## 5. Non-functional requirements
- NFR-1 Security (verifiable): (a) OWASP ASVS Level 2 baseline tracked in a checklist; (b) (replaces the draft policy of ADR-0010, which is revised before acceptance) CSP `default-src 'none'; script-src 'self' 'nonce-<per request>'; style-src 'self'; connect-src 'self'; img-src 'self'; font-src 'self'; frame-src 'none'; form-action 'self'; worker-src 'none'; base-uri 'none'; object-src 'none'; frame-ancestors 'none'` without `unsafe-eval`/`unsafe-inline` (the nonce protects the inline import map that carries the integrity data, ADR-0010), plus HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Permissions-Policy on every location, verified by an automated test that also asserts zero CSP violations during sign-in, theme and language switch, module errors and session expiry; (c) all permission checks server-side, deny by default, tested per endpoint; (d) dependency, image and secret scanning in CI of core and template, builds fail on high/critical findings, SBOM per release; (e) no personal data in application logs. The shell document is sent with `Cache-Control: no-store`; the nonce has at least 128 bits; inline style attributes needed by the window manager are set through the CSSOM and a test fails if `unsafe-inline` becomes necessary.
- NFR-2 Quality: every Maven module enforces JaCoCo line coverage >= 80 % and every frontend package enforces Vitest (v8) line coverage >= 80 %. The gate is per language and per repository; there is no cross-language average, which satisfies and tightens the project rule "global >= 80 %". CI also fails if coverage drops by more than 2 points against the baseline stored in the ref `ci-baseline` by `main` (PRD-0003 SK-2 AC2). The build emits all CSS as files and inlines no assets as data URIs (PRD-0005 VL-13 AC4). Exclusions only via a reviewed list in the build. Module repositories inherit the gate from the template. Coverage includes integration tests (Failsafe merged into the JaCoCo report); the packages `gateway`, `session` and `security` require >= 90 % line coverage; module CI produces the coverage report as evidence; the link to the contract-test kit's report is recorded at activation (PRD-0004 PF-9 AC2) and the registration checklist verifies that the gate configuration equals the template's. Module CI also signs the image (cosign) and prints the digest.
- NFR-3 i18n: no hard-coded user-visible strings; CI enforces key parity de/en and placeholder consistency; pseudo-locale visual tests.
- NFR-4 Accessibility: WCAG 2.2 Level AA for shell and modules (EN 301 549 aligned), automated axe checks in E2E tests plus a manual screen-reader pass per UI-20.
- NFR-5 Operations: single-host Docker Compose; configuration via environment and secret files; documented, tested upgrade, rollback, backup and restore. Backup: nightly `pg_dump` per database (platform, Keycloak, each module schema) plus realm export and compose/secret inventory, encrypted (age), 14 daily and 8 weekly copies on an SMB share outside the host. The SMB target (host, share, credentials) is configuration, not code (Q9, Q18). RPO <= 24 h, RTO <= 4 h. A restore onto a clean host is rehearsed before go-live and at least twice a year. The module store volume is backed up with the databases (encrypted `tar`); the session table is excluded. A restore rehearsal checks that all registry hashes match the restored store.
- NFR-6 Performance (p95, 20 concurrent users, warm cache, LAN): shell first load <= 2 s; sign-in to usable desktop <= 3 s; module window open <= 1.5 s warm / 3 s cold; core API read <= 200 ms, write <= 500 ms; SDK permission check <= 5 ms (local); window drag 60 fps with 5 windows (manual gate on the development machine with CPU throttling and software rasterisation as a proxy for weaker PCs, plus a runtime glass guard; PRD-0005 VL-8 AC3); core cold start to ready <= 60 s. Gateway budget: the gateway adds <= 15 ms p95 to a proxied call (stub upstream, 50 req/s, 20 concurrent users) and sustains 100 req/s on the target host; a load test (k6) is part of the nightly E2E run.
- NFR-7 Resource budget (host: 8 vCPU / 32 GB RAM / 500 GB disk, Q18): Keycloak 1.5 GB, PostgreSQL 1 GB, core backend 1.5 GB until measured under the FR-11 load test, target 1 GB (PRD-0003 SK-16 AC2; gateway, sessions, registry; JVM heap capped at 60 % of the limit, to be measured under the FR-11 load test), proxy 128 MB, each module backend <= 512 MB (`mem_limit`, 1 CPU). With 30 % headroom about 24 modules fit by memory; CPU, disk (images, store, backups, logs) and the 8 cores are tracked as modules are added. Exceeding the budget requires an ADR on host sizing. The template ships these limits.
- NFR-8 Observability: JSON logs to stdout with timestamp, level, service, `correlationId` (`X-Correlation-Id`), no personal content; log rotation 10 MB x 5; Spring Actuator liveness/readiness and Prometheus metrics on an internal port; Prometheus/Grafana optional (compose profile), not required in phase 1. Gateway metrics (Micrometer, tag `module` only, no user ids): `slg_gateway_requests_total{module,status_class}`, `slg_gateway_request_seconds{module}`, `slg_gateway_upstream_timeouts_total{module}`, `slg_session_active`, `slg_token_refresh_failures_total`, `slg_store_verify_failures_total`. Phase 1 alerts (AD down, break-glass use, certificate expiry, backup failure, a module DOWN for more than 5 minutes) appear in the admin overview and in the logs; e-mail alerts are not provided (owner decision Q30); alerts appear in the admin overview, the administrator tray indicator and the logs, so operators must watch the overview.
- NFR-9 Time and TLS: NTP-synchronised hosts; tokens with skew > 60 s are rejected and readiness reports drift; TLS at the proxy with a certificate from the internal Windows Active Directory CA (enrollment process to be agreed with the CA owner), trusted by all JVMs and Keycloak (also for LDAPS); certificates expiring in < 30 days raise a health warning. Two certificates are needed (shell host name and Keycloak host name); the expiry warning covers both.

## 6. UI/UX
Since revision 3 the former taskbar is the open-window list in the top bar (direction C, PRD-0005 VL-10; ADR-0003 is unchanged, this is a look decision). Its items are buttons with `aria-current`; an overflow "+n" list is a keyboard-operable disclosure; it keeps the `navigation` landmark and roving tabindex of UI-15 and UI-17.
Details apply to the shell and bind modules through the SDK, the design system and the registration checklist.

### 6.1 Window manager
- UI-1 Windows form a stack; focusing or activating raises a window; exactly one is active; minimized windows keep their stack position.
- UI-2 Opening a window moves focus into it; closing or minimizing returns focus to the opener, else the next item of the open-window list; focus is never lost to `body`.
- UI-3 Dragging to the left/right edge snaps to half, to the top maximizes. Keyboard equivalents via the window menu (`Alt+Space`, and a visible menu button as primary path because the browser or OS may intercept `Alt+Space`, notably in Edge on Windows): snap left/right, maximize, restore, move, resize. Free move and resize also have a single-pointer alternative (WCAG 2.5.7), for example step buttons in the window menu. The title bar always stays reachable; windows are clamped on viewport resize.
- UI-4 Each entry point is `singleton` (reopening focuses it) or `multiInstance` (titled "Name (n)").
- UI-5 Deep links use the History API: `/app/<moduleId>/<route>`, with the proxy falling back to the shell. The shell opens the window after authorization; unauthorized or unknown targets show the same neutral state (no leak of module existence). Only the active window is reflected in the URL; back/forward navigate within the active module route. Module backends and remotes live under `/modules/<id>/api` and `/modules/<id>/remote` (distinct from shell paths).
- UI-6 Open windows, geometry, state, stack order and module route are persisted per user and per device class (debounced). Restore loads only active and visible windows lazily. Last write wins across tabs/devices.
- UI-7 Modules work at a minimum window size of 480x320 px and reflow via container queries/ResizeObserver.
- UI-8 A module may register a close guard; the shell asks for confirmation on close, sign-out and session-expiry warning.

### 6.2 Launcher, desktop, notifications
- UI-9 Launcher lists permitted, enabled modules by manifest category with type-to-filter search, opens with `Meta`/`Ctrl+Esc`, and lists recent items. Texts come from the module i18n bundle and are sorted by active locale.
- UI-10 Users may pin modules as desktop icons (grid, stored per user); unavailable modules stay visible but disabled with the reason.
- UI-11 The tray shows clock, notification centre, and language/theme/user menu. Toasts have severity; warnings and errors do not auto-dismiss; announced via `aria-live`. Delivery and storage belong to the notification capability (not in this PRD).
- UI-12 Narrow viewport (< 768 px or coarse pointer): single-window mode with maximized window, bottom switcher, full-screen launcher, no move/resize/snap, separate stored layout. Modules may declare `minViewport`. Touch and kiosk optimization is out of scope (Q8).

### 6.3 States
Shared components: Loading (skeleton after 300 ms, spinner after 1 s, timeout message after 15 s), Empty, Error (what happened, correlation ID, Retry), Forbidden, NotFound, Offline (shell banner; modules mark stale data), SessionExpired.
- UI-13 When the gateway reports an expired or revoked session (FR-11 AC4) the shell shows a non-modal banner (`role="alert"`, localised, without moving focus) with a keyboard-reachable "Sign in again" button. It opens the login in a popup, falling back to a new tab if blocked. Completion is detected through `BroadcastChannel` or session polling, not `window.opener`. On success the shell refreshes the CSRF and permission state, keeps module state and returns focus to the previously focused control; if a different user signed in, all windows are reset. Only after failed or cancelled re-authentication are windows replaced by SessionExpired (focus moves to its heading). An idle warning 2 minutes before the idle timeout (`role="alertdialog"`, extendable) is shown (Q29, decided). Verified in the skeleton by automated tests (focus, role, popup blocked, other user) and the manual screen-reader pass.
- UI-14 A failed remote is isolated per window by an error boundary (FR-8).
- UI-30 The shell never displays problem-details `title` or `detail` verbatim. It maps `code` (with `params`) to i18n keys of the shell or the module bundle; unknown codes show a localised generic message with the correlation ID. Each module declares its error codes in the manifest and registration fails if a code lacks a de/en key; the gateway forwards `Accept-Language`.
- UI-31 Gateway 502/503/504, timeouts and network failures show the Error state with Retry (backoff) in the affected window; a failing health poll shows the Offline banner (`role="status"`), because `navigator.onLine` is unreliable; 401 shows UI-13; 403 shows Forbidden; a module disabled while open shows an Unavailable state. Loading regions set `aria-busy`.

### 6.4 Keyboard model
- UI-15 Skip links; roving tabindex in the open-window list and desktop icons; `F6`/`Shift+F6` cycle shell regions; configurable window switch shortcut; `Alt+Space` window menu; keyboard move/resize (arrows, `Enter` confirm, `Esc` cancel); `Esc` closes menus and popovers, never windows; the window menu follows the menu keyboard pattern (arrows, Home/End, roving tabindex, Tab closes it); `?` shows shortcuts. Modules register shortcuts only through the SDK. Single-character shortcuts (`?`, type-to-filter) are inactive in editable fields. Every shortcut is listed in the `?` help, exposed through `aria-keyshortcuts` and can be remapped or disabled. Defaults avoid browser and OS reserved keys: `F6`, `Ctrl+Esc` and `Ctrl+Alt+Arrow` are replaced if they fail the Edge/Windows check; SDK shortcut registration rejects collisions. Esc precedence: move mode, then menu, then dialog. Keyboard move/resize mode shows a visible indicator and announces entry and exit.
- UI-16 No keyboard traps. Modal dialogs are scoped to their window (the window's other content and other windows are inert, the launcher and the open-window list remain operable) and return focus to the invoking control; shell-level dialogs are page-modal. Dialogs focus the least destructive control first; Escape cancels. If the launcher opens another window while a dialog is open, the new window opens behind the dialog and the dialog keeps focus.

### 6.5 Screen reader semantics
- UI-17 The desktop is a document, not an `application` role. Landmarks: open-window list in the top bar (`navigation`), active window region (`main`), tray (`complementary`). Each window is a labelled non-modal dialog/region. DOM order = tab order = visual stack order; no positive `tabindex`. Non-active windows are listed in the open-window list (`aria-current`) and minimized content is `inert`. When all windows are minimized the desk is the `main` landmark. Raising a window must not drop focus from a focused control, whether by `Element.moveBefore()` or by `z-index` stacking with a documented tab-order exception (verified in the skeleton). Raising a window by pointer or Tab never blurs a focused control (automated test: type after clicking and after Tabbing into a background window; iframe content is not reloaded). Tab order visits background windows before the active one (WCAG 2.4.3); this is a documented trade-off mitigated by skip links and F6. Windows are `region` landmarks with `aria-labelledby`; modules must not emit `main` or `h1`; `document.title` is "<window title> - SLG OS".
- UI-18 Window open/close/minimize/switch is announced through a polite live region; repeated identical messages are made distinguishable. Free move and resize have a single-pointer alternative (step buttons in the window menu, WCAG 2.5.7) and a keyboard alternative (WCAG 2.1.1).
- UI-19 Each window's title is its `h1`; module headings start below it.
- UI-20 A manual screen-reader pass (NVDA + Firefox, JAWS + Chrome, VoiceOver if used) is part of the release checklist for shell changes.

### 6.6 Design system and theming
- UI-21 One versioned package `@slg-os/design-system` (React components on Bootstrap 5.3, shared as a Module Federation singleton) with `--slg-*` design tokens mapped onto Bootstrap variables. Button and text tokens meet WCAG AA on every shell background (Bootstrap's default `btn-outline-secondary` fails contrast on tertiary backgrounds); the launcher and shell reflow without horizontal scroll at 320 CSS px (WCAG 1.4.10), while 360 px stays the supported minimum for narrow mode; tokens meet 4.5:1 for text and 3:1 for non-text elements and focus indicators, and focus remains visible in forced-colors mode. The visual language is defined in PRD-0005. Its deliberate brand deviations are: dark text on the primary colour `#00aeef` (white on it is 2.53:1), darker link and focus tokens, weight 300 only at 20 px and larger, pill-shaped single-line controls, and Source Sans 3 instead of the company face. The primary button's fill is identified by its label (5.98:1) and not counted as a 3:1 boundary (PRD-0005 VL-2 AC4, Q57). Modules use tokens and components only; raw hex colours, global CSS, own Bootstrap build, `!important` and global selectors are rejected by a lint rule in the template and by the registration checklist. iframe-embedded tools are an exception that requires an ADR and must provide a meaningful title, focus hand-off and theme/language signals where possible (Q21).
- UI-22 The shell sets `data-bs-theme` on `<html>`; modules must render correctly in both themes, never read `prefers-color-scheme`, and switch live. Default: OS preference at first login, then the user's choice. A contract test renders the reference module in both themes.
- UI-23 Respect `prefers-reduced-motion` and `forced-colors`; 200 % zoom and 400 % reflow without loss of function. No animation may exist without a `prefers-reduced-motion` rule; a test enforces this.

### 6.7 i18n and locale

The spike default `en` is replaced by this order. Before sign-in the language is the browser language, then `de`; the Keycloak login theme and the popup pages are bilingual and themed; the preference is stored server-side per user. The English fallback of a name carries `lang="en"`.

A missing key falls back to `en`, then shows the key and logs a warning (a defect). CI checks parity, unused/missing keys and placeholders. Registration is rejected if either language is incomplete.

- UI-28 Layouts tolerate +35 % German text length; a pseudo-locale (`de-XL`) is used in dev builds and visual tests; icons never carry meaning alone.

## 7. Data and interfaces
- PostgreSQL for platform data (registry, group mappings, preferences/layouts, audit log); versioned migrations.
- Module database provisioning: after the manifest passed validation (a rejected submission creates nothing) the provisioner (a separate container with its own privileged database role and no route from the public proxy; PRD-0004 PF-4) creates schema `mod_<id>` and role `mod_<id>` limited to its own schema and delivers the credentials as files under `/run/secrets/` (mode 0400, never logged) by the mechanism to be fixed in ADR-0018 (fallback: operator-written secret files, Q46); the same step provisions the module's Keycloak audience, scope and service-account client (FR-4). Modules run their own Flyway migrations at startup with that role; failure keeps readiness DOWN and the previous container running. Migrations must be backward compatible with the previous module version (expand/contract) to allow rollback.
- Shell document: the core generates the shell HTML per request with a CSP nonce and an inline import map whose `integrity` section lists the SHA-384 hash of every registered JavaScript file; the map and the module list come from the same registry snapshot, and an unlisted module file is an error (ADR-0010).
- Contract artifacts: manifest schema (versioned JSON schema), SDK, REST conventions (versioned, OpenAPI, breaking-change diff in CI), federated remote conventions.

## 8. Security and data protection
- 8.1 OIDC and session (ADR-0012): the core is a confidential client using authorization code + PKCE (S256) with exact redirect URIs (no HTTP redirect URIs in production). Tokens stay on the server: the browser holds an `HttpOnly`, `Secure`, `SameSite=Strict` session cookie (or `Lax` under the fallback of FR-11 AC1); CSRF protection per FR-11. Access tokens <= 5 min; rotating single-use refresh tokens with serialised use; idle timeout 30 min, absolute session 10 h. Kerberos/SPNEGO SSO is not enabled (Q1). Module backends accept bearer tokens forwarded by the gateway and validate issuer, per-module audience, signature (cached JWKS), expiry and `azp`.
- 8.2 Logout and revocation: RP-initiated logout; back-channel logout (delivered from Keycloak to the core over the internal compose network, not through the public proxy) invalidates the server-side session at once, so no denylist is needed. A user disabled in AD or a changed group loses access within the Keycloak LDAP sync interval (set to 10 min) plus one module-token lifetime (5 min), which meets the 15-minute target of Q7. Administrators can revoke all sessions (audited).
- 8.3 Trust boundary of federated remotes: remotes run in the shell origin. With the BFF a compromised module build cannot read or exfiltrate a token, but it can still send authenticated requests as the signed-in user, read other windows' DOM and send data to same-origin endpoints; `connect-src` does not stop exfiltration by navigation, prefetch or WebRTC. Backend authorisation per request therefore stays the enforcement point, and ADR-0007 is a security control: only admin-approved remote entries on the platform origin are loaded; integrity of every JavaScript file is enforced through the import map and the immutable content-addressed store (FR-4 AC7, ADR-0010; verified in Chromium; the Firefox check is a release gate (Q25a); WebKit runs informatively in CI. Integrity enforcement is claimed only for browsers where a CI test proves it, and the shell refuses to load module remotes (error page, audited) in browsers outside the supported list); CSS, JSON and other runtime-fetched files are not covered, so registration restricts file types; the release of a version is a reviewed process in the module repository: the tool records the review reference at activation and neither verifies it nor enforces a second approver (owner decision Q38); no external CDNs or scripts at runtime; module CI uses locked dependencies, scanning and signed images; the shell never renders module-supplied HTML. Down-scoped module tokens are not a boundary against a hostile module. The owner accepted the remaining risk on 2026-10-19 (Q24); it includes that one person with repository write access and one administrator can activate hostile code, because the release review is a process and not a tool control (Q38). The gateway cannot tell which module's script issued a same-origin request, so a compromised module can call any module API or core endpoint the user may call; mitigations are least-privilege role mapping, step-up re-authentication for administrative actions (FR-11 AC7), per-module backend authorisation and ADR-0007, and no further isolation is claimed.
- 8.4 Service-to-service: each module backend has a Keycloak service account (client credentials) with audience-restricted least-privilege scopes, secrets delivered as files under `/run/secrets/` (0400) and rotated at least yearly. User identity reaches modules only through the gateway-forwarded, audience-bound token. A module backend accepts a bearer token only if issuer, signature, expiry and audience match and `azp` is the core BFF client (forwarded user tokens) or a registered service-account client (module-to-module). Each target module lists the caller modules allowed to call it; the caller's token carries the target audience only if allowed. A user id passed between modules is informational and never used for authorisation. Module containers are on an internal network, not published on host ports.
- 8.5 Reverse proxy: only the proxy is exposed (TLS 1.2+, HSTS). Keycloak is served from its own origin (a separate host name), not under the shell origin; only the login, logout, token and well-known endpoints are exposed publicly, the admin console and the master realm are not (Q27). Header stripping and traversal tests run against the production module locations with positive assertions (404/400 and no content), and identity headers are handled by an allowlist. It strips inbound `X-Forwarded-*`, `Forwarded` and identity headers and sets them itself; backends trust such headers only from the proxy network; identity comes from validated tokens, never headers. Keycloak has `frame-ancestors 'none'`, empty web origins and exact redirect and post-logout URIs; the shell CSP is tested against the full login and logout redirect chain (including `form-action`); the core reaches Keycloak by the public issuer URL through a Docker network alias.
- 8.6 Manifest validation and SSRF: JSON schema validation with size limit; server-side fetches only to an allowlist of internal module service names, http(s) only, fixed ports, no redirects, resolved IPs must not be loopback, link-local or metadata addresses, 5 s timeout. The connection is made to the validated IP (no second DNS resolution, against rebinding), and the allowlist is derived from registered module entries, not from manifest content.
- 8.7 Keycloak and AD (service account and certificate rotation operated by the owner's team, Q20): LDAPS with certificate validation; dedicated read-only AD service account limited to the needed OUs; brute-force detection with tuned parameters; explicit refresh-token and session lifetimes; no `start-dev` mode; the built-in client scopes are defined explicitly in the committed realm file (importing a realm with custom scopes otherwise drops `profile`, `email`, `roles`, `web-origins`) and an import smoke test checks them; admin console not routed via the public proxy; realm export contains no secrets; defined patch cadence.
- 8.8 Audit log integrity: see FR-9. Exports go to the read-only backup.
- 8.9 Data protection (DSGVO): personal data processed by the core: user id, display name, email, AD group names (server-side session), IP address (audit), UI preferences, technical logs, and session data (session id hash, IP, user agent, encrypted tokens). Purpose: authentication, authorization, security accountability, operation. Legal basis proposal: Art. 6(1)(f) DSGVO and § 26 BDSG; a works council agreement is required before go-live because login and audit data could enable behaviour or performance monitoring (BetrVG § 87(1) Nr. 6); the audit log is not used for performance evaluation. Retention (owner decision; the owner stated on 2026-10-19 that no restriction applies, the position is a statement of intent, not a clearance; the formal DPO and works-council agreement stays a go-live item under Q23, which this document does not assert as given; Keycloak's own event store, kept 7 days, is personal data too): preferences are removed 90 days after the user disappears by the daily job of PRD-0004 PF-14 AC2; audit log 6 months, application logs 30 days, session data until logout or the absolute timeout plus 24 hours, preferences 90 days after the account disappears from AD. Audit log access for platform administrators (no auditor role in phase 1, Q14), the access itself audited. Logs contain pseudonymous ids, never names, emails or content. An Art. 30 record is created and the DPO decides on a DPIA before go-live. The core can export and delete a user's preferences and look up audit entries on request.
- 8.10 Secrets: files under `/run/secrets/` (mode 0400; static ones as Compose secrets, per-module credentials from the provisioner, section 7), never logged, no secrets in images, repositories or realm export, per-module DB credentials.

## 10. Rollout and operations
- Topology: compose services `proxy` (shell assets and, after an `auth_request` check against the core, module files from the read-only store volume; TLS for both host names), `keycloak` (own host name), `postgres`, `core-backend` (API, gateway, shell document), from phase 1b `provisioner` and the backup container, `ldap` in the test profile, plus modules; no separate shell container. Startup: the core waits for postgres (healthy), Keycloak waits for postgres, the proxy depends on the core being started only (upstreams are resolved per request); Keycloak is not a start dependency of the core. The core starts when Keycloak is absent and reports readiness DEGRADED (sign-in unavailable) instead of failing; modules start after the core-backend and retry. An E2E test starts the stack with Keycloak delayed and expects readiness DEGRADED, then UP (PRD-0003 SK-16 AC1).
- Deploy/discovery: modules publish semver-tagged images to GitHub Container Registry (ghcr.io; the host pulls, outbound connections are allowed, Q10/Q18) and a manifest. An administrator first submits the manifest (provisioning, FR-4), then the operator adds the compose file for the module (pinned by image digest) and starts it, then the build is registered and activated (PRD-0004 PF-4, PF-5). Module API calls go through the core gateway (FR-11); `/modules/<id>/remote` is served from the immutable content-addressed store (long-lived `immutable` cache headers for hashed files, `no-store` for the registry) and proxy locations are generic (`/modules/<id>/remote/<version>-<treeSha256>/` with an id pattern), so no proxy change or reload is needed on registration; the registry, not Docker labels, is the source of truth. The core polls module health (FR-10); modules send no heartbeat.
- Upgrade/rollback: register the new version (state `registered`), change digest, `up -d <id>`, readiness-gated, then an administrator activates it after the pre-flight checks (PRD-0004 PF-5); rollback = previous digest, permitted because migrations are expand/contract. Core upgrades follow the same path after a backup.
- Contract versioning: SemVer `major.minor`; minor is additive, major is breaking. The platform supports only the current major (Q13): a breaking contract change is released together with updated modules, and modules not yet updated are disabled by registration validation until they are. React major and design-system range are pinned per contract major.
- Failure modes: AD down: existing sessions work, new logins fail with a localized error and an alert. Keycloak down: the gateway keeps valid module tokens until they expire (<= 5 min), then answers 401 `AUTH_UNAVAILABLE`; sessions are kept. PostgreSQL down: 503 `SESSION_STORE_DOWN` (FR-11 AC8). Core restart: sessions persist, in-flight requests fail and the SDK retries once. Module down: window error boundary (FR-8) and 503 `MODULE_DOWN`. Module backends refetch the JWKS on an unknown key id.
- Phase 1a (walking skeleton, PRD-0003): proxy with two host names, production-mode Keycloak with LDAP, core with BFF and PostgreSQL sessions, minimal registry with content-addressed store and import map, audit table, shell with two windows, idle warning and session-expiry flow, reference module with minimal SDK, CI with coverage gates, E2E in Chromium and Firefox (WebKit informative), backup script.
- Phase 1b (PRD-0004, with the visual language PRD-0005 alongside): admin UI and permission management, audit chain and event ingestion, provisioner, store completion and staged activation, full SDK, contract test kit and module template, alerts, backup completion, privacy tooling.
- Phase 1c (go-live gates): restore rehearsal on a clean host, Firefox and Edge checks (Q25a), load test, manual screen-reader pass, Q23 and Q25a closed.
