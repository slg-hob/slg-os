# PRD-0004: Platform capabilities (phase 1b)

- Status: Reviewed (four independent reviews integrated, awaiting owner approval)
- Owner: Benjamin Honauer
- Date: 2026-10-19
- Related ADRs: 0001, 0002, 0004 to 0009, 0010 and 0011 (proposed, decided by the skeleton evidence), 0012; ADR-0013 to 0016 and 0017 (written by the skeleton, PRD-0003 section 7.5). New ADRs written during this phase: section 7.5 (numbered from 0018).
- Related PRDs: PRD-0001 (platform core, approved revision 2), PRD-0003 (walking skeleton, approved; this PRD builds on its code and its decisions)
- Related: `ROADMAP.md` (phase 1b), `docs/reviews/module-registration-checklist.md`

## 1. Problem and goals
After the skeleton, one reference module runs through the real stack, but everything that makes the platform usable by a team is missing: administrators can only act through an API, the audit log is a plain table, module databases and Keycloak clients are provisioned by a script, the immutable store has no retention or monitoring, module authors have no SDK package and no template, and nobody is told when something fails. Phase 1b adds these capabilities so that a second team can build, register and operate a module without help from the core developers.

Goals:
- G1: An administrator manages modules, roles, group mappings, sessions and the audit log in an accessible, bilingual admin UI, with every sensitive action step-up protected and audited (PRD-0001 FR-4, FR-4a, FR-5, FR-5a, FR-9).
- G2: The audit log is tamper-evident (hash chain, daily verification), is fed with Keycloak login events, has a retention job and a read path (FR-9, ADR-0008, 8.9).
- G3: Registering a module provisions its database schema and role, its Keycloak audience, scope and service-account client automatically, idempotently and without handing a privileged credential to the module or to the request-serving core (FR-4, section 7).
- G4: The immutable module store is complete: archive input, verification at start and daily, retention, monitoring and a staged activation flow (FR-4 AC7).
- G5: The module contract is usable by other teams: published backend and frontend SDK, a contract test kit, an automatable part of the registration checklist, and a module template that passes the checklist without edits (FR-6, FR-7).
- G6: Operators see problems: alerts for AD, break-glass use, certificates, backups, modules, store and audit chain in the admin overview (NFR-8, NFR-9).
- G7: Backups are scheduled, include the store and all module schemas, report their result to the platform and can be written to the SMB target (NFR-5).
- G8: Data-subject requests (export and deletion of preferences, lookup of audit entries) can be served by an administrator (8.9).

## 2. Non-goals
- Visual language, window chrome look and desktop metaphor (own PRD, ROADMAP). The admin UI uses the design-system components of the skeleton plus the patterns of PF-7.
- Go-live gates of phase 1c: restore rehearsal on a clean host, full load test, chaos tests beyond those listed here, Firefox/WebKit/Safari/Edge manual checks, manual screen-reader pass, works council and DPO sign-off.
- E-mail alerts (Q30, deferred by the owner); alerts stay in the admin overview, in an administrator-only tray indicator and in the logs. The notification centre and a module notification API (UI-11) remain deferred.
- An auditor role (Q14); split admin roles as a tool boundary (Q38 context); high availability; WebSocket; Kerberos (Q1); languages beyond German and English.
- The notification and job-scheduling capabilities for modules ("later" in ROADMAP) and any business module.
- Support for more than the current contract major (Q13); self-service registration (ADR-0007, Q16).

## 3. Users and roles
- Platform administrator (`platform-admin`, seeded in the skeleton by `SLG_BOOTSTRAP_ADMIN_GROUP`): full admin UI and API. The owner decided that the four-eyes release of module versions is a **process**, not a tool function (Q38). The admin API uses one permission per capability (`platform.modules.manage`, `platform.access.manage`, `platform.sessions.revoke`, `platform.audit.read`, `platform.overview.read`, `platform.privacy.manage`), all bundled in the built-in role `platform-admin`. These are naming and mapping units, **not a security boundary**: `platform.access.manage` lets its holder grant himself or herself every other permission, so it is equivalent to full administration. The migration maps the skeleton's single `platform-admin` check (PRD-0003 SK-6, SK-7) onto the six permissions; the step-up list of PRD-0003 SK-7 AC6 is a subset of the list in section 8.
- Module developer: consumes the SDK packages and the template, runs the contract test kit in module CI.
- Platform team reviewer: applies `docs/reviews/module-registration-checklist.md` and records the four-eyes review in the module repository.
- Operator: runs backups, reads alerts, performs lock-out recovery.
- End user: unchanged; sees only effects (launcher, error states).

## 4. Functional requirements
Numbering `PF-n`. "Implements" names the PRD-0001 requirement. Sensitive endpoints require step-up as defined in section 8. Each AC carries a verification type in the traceability table of the verification report: auto (CI test), doc (CI check that a document statement exists) or manual (recorded evidence).

### 4.1 Audit log

#### PF-1 Tamper-evident audit chain
Implements FR-9 AC2, 8.8.
- AC1: Every `audit_event` row stores `seq` (a gapless integer), `prev_hash`, `row_hash` = SHA-256 over a canonical encoding of `seq`, `prev_hash` and all event fields, and `detail` (JSONB; permission names, ids and before/after values only, size-limited, no secrets, no free text, included in the hash). Because PostgreSQL requires the partition key in every primary key, the table is `audit_event_v2` partitioned by month (UTC) with primary key (`seq`, `occurred_at`); the chain is defined across partitions by `seq`.
- AC2: Migration from the skeleton's table: create the new table, copy and re-chain existing rows in batches ordered by `seq`, swap the names in one short transaction (lock timeout 5 s, retried), record an `audit_checkpoint`. Test on 1,000,000 generated rows: duration <= 5 minutes and maximum lock hold <= 2 s; the grants of PRD-0003 SK-9 (append-only for `slg_app`, no `TRUNCATE`, `ALTER`, `DROP`) are re-applied and tested after the swap.
- AC3: Writer: `seq` comes from a one-row `audit_head` table. For audited admin and security actions the audit insert runs **in the same transaction as the change** (fail closed: no audit entry, no action), and the lock on `audit_head` is taken as the last statement before commit, so it is held for microseconds and a rollback consumes no `seq`. Benchmark with two core containers at 50 events/s: p95 insert <= 20 ms, zero gaps (a gap fails the test).
- AC4: Verification: a daily job (and the admin action "verify now") reads the **whole retained range** in a `REPEATABLE READ` snapshot in keyset batches up to the head at start, while inserts continue, and recomputes the chain. Checkpoints (AC5) anchor the start of the range only after retention. It reports OK, first broken `seq`, or gap, and compares the head with the head recorded in the previous `job_run` result and in the latest backup status record (PF-15 AC3): a head with a lower `seq` than recorded is reported as truncation. A failure raises an alert and writes an audit event. Tests: modified field, modified old row, deleted row, inserted row, reordered rows, truncated tail. A CI performance test verifies 1,000,000 rows within 10 minutes (budget doubled for CI variance in the PR gate; measured in the nightly run).
- AC5: Checkpoints are written only by the retention function (PF-3 AC1), carry an HMAC under a key that the application role cannot read, and are themselves chained; verification checks the signature and `seq` continuity across checkpoints.
- AC6: The head hash and `seq` appear in the verification log line and in the backup status record. The chain protects against casual or accidental change by anyone who cannot rewrite the whole table and the checkpoint key; it does not protect against a database superuser or someone holding the HMAC key. This limit is stated in the operator documentation (doc check) and in section 8. Q45 asks whether an external anchor is wanted.

#### PF-2 Keycloak event ingestion
Implements FR-9 (failed login, break-glass), 8.7.
- AC1: The core polls the Keycloak **events** endpoint of the platform realm and of the master realm every 30 s over the internal network, using two read-only service accounts that hold `view-events` in their own realm only (`slg-audit-reader` for the platform realm, a separate account for the master realm; neither holds `view-realm` or `query-users`). Cursor = last event time minus a 60 s overlap; events are de-duplicated by a key over (time, type, user id, session id, client id, IP); pages of 500 until empty; a poll after a Keycloak outage resumes from the cursor. The realm file sets `eventsExpiration` >= 604800 s; the import smoke test asserts it.
- AC2: What is written. `LOGIN` and `LOGOUT` stay written by the core (PRD-0003 SK-9); ingestion writes `LOGIN_ERROR`, master-realm logins and `break_glass_use`. A Keycloak `LOGIN` without a matching core entry within 60 s is a discrepancy: a log line and the alert kind `login-audit-gap`. "Exactly one entry per source event" applies per event type, tested with a replayed and an overlapping poll including equal timestamps.
- AC3: Data minimisation: the realm file turns off storing the typed username in event details (`includeRepresentation` and detail filters) and the free-text username is never copied. Failed-login rows hold the user id only if Keycloak resolved one (else `unknown`), a reason code, and the IP truncated to /24 (IPv4) or /64 (IPv6); `break_glass_use` keeps the full IP. Test: a failed login with a password-like username leaves it nowhere in the core database, logs, backups, **or Keycloak's own event store and admin console**.
- AC4: A master-realm login that is not the documented break-glass account, and any use of the break-glass account, raises an alert and an audit event.
- AC5: Latency up to two poll intervals (60 s) is documented. Ingestion is a configuration switch. The owner stated on 2026-10-19 that no data-protection or works-council restriction applies to what the platform needs, so it may be enabled in shared environments; the formal DPO and works-council sign-off remains a go-live item under PRD-0001 Q23 (this PRD does not assert it has been given).

#### PF-3 Audit retention, read access and export
Implements 8.9, FR-9 (reads audited), Q6, Q14.
- AC1: Retention 6 months (configurable, Q6 working value), applied in whole months. The retention job calls a `SECURITY DEFINER` function owned by `slg_retention` that computes the cut-off in the database, and in **one transaction** detaches the partition, writes a signed checkpoint (last `seq`, last `row_hash`), checks that the first remaining row's `prev_hash` equals the checkpoint hash, and commits; the `DROP` follows after the commit and is retried. The function cannot write `audit_event` rows and cannot detach a partition newer than the cut-off. Tests: crash between the steps, an empty month, a month boundary in UTC, the application role cannot detach or drop.
- AC2: `GET /core/api/v1/admin/audit` (permission `platform.audit.read`) filters by time range, event type, actor, object and outcome with keyset pagination; page size <= 200. Every call, including exports, writes an `audit_read` event with the filter used (not the result). Filter inputs are validated (identifier formats), and the audit entry stores a hash of a free-form search term.
- AC3: CSV export of a filtered range (at most 50,000 rows; the UI shows the cap before download and reports truncation). One shared CSV writer is the only way to create CSV in the core (ArchUnit rule); it trims leading whitespace and control characters, always quotes, and prefixes cells that then start with `=`, `+`, `-`, `@`, tab or carriage return with an apostrophe. UTF-8 with BOM, header row. Hostile-value tests include `\u0000=`, a leading-space formula such as " =cmd", `\n=`, DDE payloads. Export requires step-up and is used by PF-14.
- AC4: The audit viewer shows event types by code mapped to i18n keys (PF-7 AC7).

### 4.2 Provisioning and the store

#### PF-4 Module provisioner
Implements FR-4 (provisioning sentence), section 7 (module database provisioning), 8.4, 8.10.
- AC1: Order of a first deployment (this supersedes "operator adds the compose service, then registers" in PRD-0001 §10, C15): (1) the administrator submits the manifest; (2) the provisioner creates, idempotently, the schema `mod_<id>` and its database role(s), the Keycloak audience, scope and service-account client, and the credential files; provisioning does not need a reachable module; (3) the operator starts the module container; (4) the build is fetched or uploaded and the version becomes `registered` (PF-5); (5) an administrator activates it. A re-run changes nothing; a partial failure leaves a recorded state and a re-run completes it. Deleting a module does not drop its schema; data is removed only by a separate "purge module data" action (PF-7, section 8). Registering a deleted id reuses the old schema only after the administrator confirms; otherwise it is refused with the code `SCHEMA_EXISTS`.
- AC2: **The provisioner is a separate container** (`provisioner`), reachable from the core only through an internal API with per-call authentication (mutual TLS or a signed request with a replay window). Its database and Keycloak credentials are mounted only into that container; the core container has no mount, variable or network route that exposes them. `slg_provisioner` can create schemas and roles but cannot read platform tables or module data, and a read-only `slg_backup` role exists for PF-15. CI asserts that the core container cannot read the provisioner's secret paths, that the runtime role fails `CREATE ROLE`, and that `slg_provisioner` cannot `SELECT` platform or module tables.
- AC3: Keycloak rights: with fine-grained admin permissions (v2) the provisioner may manage only clients whose id starts with `mod-`; it cannot modify the core client, `slg-*` clients, realm settings or realm role mappings. CI asserts 403 when the provisioner token edits the core client, adds a realm role mapping or creates a client without the prefix. If Keycloak 26.8 cannot express this, ADR-0018 records the residual risk and adds a daily diff of all non-module clients against the committed realm file with an alert on drift.
- AC4: Credentials never appear in the manifest, registry, audit log, logs, images, environment variables or `docker inspect` output; they reach the module container only as files under `/run/secrets/` (mode 0400, owned by the container user). The delivery mechanism is decided in ADR-0018 by a spike in B2a against the criteria of Q39. A CI test generates canary secrets and greps stack logs, `docker inspect`, database dumps and the backup archive for them, and asserts the module starts with its files.
- AC5: Rotation: the administrator action "rotate credentials" (step-up, audited) issues new credentials. Database overlap uses two roles per module (`mod_<id>_a`, `mod_<id>_b`, same grants, alternating on rotation) or an announced restart window if the spike shows two roles are not workable; Keycloak secrets use the client secret rotation with a grace period. The spike must demonstrate rotation with a module restart and no failed request after the restart. An alert reminds yearly rotation (8.4).
- AC6: Module Flyway migrations run with the module role at module start (module concern). `/info` and the readiness endpoint report the module and schema version (PF-8 AC1); the registry records them. A module whose migration failed keeps readiness DOWN and the previous container serving.

#### PF-5 Store completion and staged activation
Implements FR-4 AC2, AC3, AC7, 8.3.
- AC1: Build sources: an archive (tar.gz or zip, uploaded to the admin API after authentication and step-up, size limit enforced before parsing, or fetched under the SSRF rules) in addition to the HTTP listing of the skeleton. Extraction uses a fresh staging directory on a quota-limited area and never follows existing links; limits: archive size, entry count, path length, a total unpacked-bytes cap (default 200 MB), a decompression-ratio cap and a wall-clock limit. Rejected: `..`, absolute paths, drive letters, backslashes, NUL, symlinks, hard links, device files, HTML files, unknown types, duplicate entries, case-insensitive and Unicode-normalisation collisions, nested archives, data prepended to a zip. Tests cover each case plus malformed archives and a fuzz corpus.
- AC2: Verification: the core verifies the active store directory of every module at start and daily (tree hash and file hashes against the registry); a mismatch disables the module's remote, raises an alert, increments `slg_store_verify_failures_total` and is audited. A restore re-verifies (PF-15).
- AC3: Retention: the three previous versions of each module and every version younger than the absolute session lifetime (10 h) stay; an audited admin job removes older ones; store volume usage is monitored and alerts at 70 %.
- AC4: Lifecycle: registering a version creates it in state `registered` (not served). Activation is a separate admin action (step-up) that first runs pre-flight checks: backend readiness UP and reported version equals `manifest.version`, `requires` satisfied, store verified, provisioning complete, and the permission diff. The UI shows the diff as a table (change type as text, permission, affected role and group mappings); breaking changes need an explicit confirmation of the listed items. Rollback re-activates the previous version in one action and shows the reverse diff. All transitions are audited and idempotent. Activation needs no second person (Q38); the audit entry names the actor and the review reference the administrator enters, validated as an https URL on an allowlisted host pattern (default `github.com/<organisation>/`) and rendered as text with `rel="noopener noreferrer"`.
- AC5: Upgrade order guidance (backend first, then remote; rollback in reverse) is shown with a warning when the reported backend version differs from the manifest.
- AC6: Icons: the manifest `icon` is an identifier from the design-system icon set; uploaded SVG icons are not supported (a module SVG would execute in the shell origin). A custom icon is a PNG within size limits and checked by magic bytes.
- AC7: Migration from the skeleton: existing `module_version` rows become `active` or `previous`; the skeleton's E2E tests and the reference-module registration call `activate`; a first version also needs activation (C16).
- AC8: Manifest strings are normalised at registration: control and bidi-override characters are rejected with the field path; limits name 60, permission label 120 characters.

### 4.3 Access management

#### PF-6 Roles, mappings and effective permissions
Implements FR-5, FR-5a, ADR-0006.
- AC1: Roles are platform-owned bundles. Administrators create, rename and delete roles, change their permissions, and import a module's `suggestedRoles` as a starting point (never automatically). The built-in role `platform-admin` cannot be deleted or reduced; the last admin mapping stays undeletable (PRD-0003 SK-6 AC2).
- AC2: Group mappings connect an AD group (full group path claim) to roles. The group picker lists groups from Keycloak within the scope of Q41. A mapping to a group that no longer exists is flagged "orphaned" and kept; mappings of permissions removed by a module upgrade are flagged "orphaned permission" and listed, never deleted silently.
- AC3: Effective-permission explanation: for a user (found by display name or login, resolved to the id) the admin sees the groups of the latest live session with its time, or "unknown, no session" and a group-based what-if instead, then mapped roles, resulting permissions and which role and mapping grants each one; a permission the admin selects to test is shown as "denied (no mapping)" when absent. The lookup is audited with the user id only. The same view serves "what would this group get".
- AC4: Effect of changes: a mapping or role change drops the permission cache (module-side caches stay stale for at most 60 s, so Q7's 15 minutes still bounds the effect together with the token lifetime), invalidates cached module tokens for affected sessions and writes one audit event per change with before and after in `detail`. Concurrent edits use optimistic locking (version column); the loser sees what changed and may apply the change again.
- AC5: Revoke sessions for one user or all users (audited, step-up); the acting administrator's own session survives "revoke all" unless chosen otherwise.
- AC6: Deny by default is verified by an exhaustive test: every mapped admin endpoint (listed by reflection) returns 401 without a session, 403 without its permission even when all other permissions are held, 403 without CSRF and Origin, and requires step-up where specified. Free-string inputs (`user`, `group`) are validated against identifier formats.

### 4.4 Admin UI

#### PF-7 Admin UI
Implements FR-4, FR-4a, FR-5, FR-9, FR-10, NFR-4 for administrators.
- AC1: The admin UI is part of the shell (core windows, not a federated module), shown in the launcher category "Administration" only to users holding at least one platform permission; deep links `/app/platform/<page>` return the neutral not-found state for others. It remains usable while any module is down (FR-8 AC3).
- AC2: Pages: Overview (alerts, module status, store usage, last backup, certificate expiry, audit chain state, session count; FR-10 health aggregation is the per-module and per-dependency status table with last check and reason), Modules (list, versions, register, activate, rollback, disable, enable, delete, rotate credentials, purge data, provisioning step list), Access (roles, mappings, effective permissions, revoke sessions), Audit (viewer and export), Privacy (PF-14), Operations (job list with run now, verification actions). The module detail page shows provisioning as a step list (schema and role, audience, scope, client, credential files) with state done, failed or pending as text, the last error code (i18n key, no secret), time and an idempotent audited "Retry provisioning"; a version with failed provisioning shows a "provisioning incomplete" badge and cannot be activated; the registration API returns the same error code so the module author's CI sees it.
- AC3: Every destructive action shows a confirmation naming the object, the consequence and the audit effect, focuses the least destructive button and, for role deletion and mapping removal, shows the number of affected groups and live sessions. The primary button of an activation names the module and versions.
- AC4: Step-up inside a window never uses a full-page redirect while a form is dirty. The flow uses the popup design of PRD-0003 SK-11 AC5: a dialog (`role="dialog"`, title, focus trap, scoped to the window) opens, on success focus returns to the triggering control and the request is replayed once with an idempotency key, on cancel or failure the entered data stays and the error is announced via `role="alert"`. Test: Playwright, keyboard only, with `auth_time` forced stale.
- AC5: Tables use the data-table pattern: header semantics, `aria-sort` on client-sortable columns, a fixed newest-first order for the audit viewer, Newer/Older buttons with the page size, a live-region count ("Showing N entries"), filters in the URL for deep links, a labelled filter form with an "Active filters" summary and remove buttons, date-time inputs that state the time zone (display in the browser's zone with explicit offset, export in UTC), and focus on the table heading after paging. In narrow windows (< 600 px) tables reflow to labelled key/value cards or scroll inside a focusable region with a sticky first column.
- AC6: Forms validate on the server. A violation carries `code`, `path` and typed `params`; the UI and the kit map it to a message, and the API adds an English `detail` for logs and CLI use only. The form focuses the first invalid field, shows an error summary with links (`role="alert"`) and links each error with `aria-describedby`.
- AC7: i18n contract: every enum or message the API returns to the admin UI (audit event type and outcome, alert kind, severity and state, job name, module and version state, pre-flight check id, Keycloak reason code, verification result, provisioning step) is a stable code; the API never returns display text. The UI maps each to a key in namespace `platform` (de and en); a CI test enumerates the codes of each enum and fails when a key is missing; an unknown code renders a generic label plus the code. Alert subjects and manifest strings are data and are not translated.
- AC8: Manifest strings render as text only. Truncated text is reachable through a focusable disclosure (WCAG 1.4.13), never a hover-only tooltip; wherever a permission label is shown, its technical name is shown too. Layout tests run with the pseudo-locale in narrow mode for every admin page.
- AC9: Accessibility: status never by colour alone; orphaned and error states are text badges; the group picker is an ARIA 1.2 combobox with asynchronous search and result-count announcement; the alerts tray indicator has an accessible name ("3 open alerts") and updates through a polite live region; axe is clean in light, dark, forced-colors and narrow mode (PRD-0003 SK-18 AC2 rules); keyboard-only completion and live-region text are asserted by Playwright (`getByRole('status'|'alert')`), not by axe; sorting uses `Intl.Collator` (umlaut test).
- AC10: Design-system additions are an inventory with a definition of done each (keyboard specification, states, pseudo-locale, forced-colors, axe, catalogue page): data table, form layout, confirmation dialog, status badge, tabs, combobox, diff table, step list, live-region helper, disclosure. The catalogue page is built first; admin pages start after data table, form and dialog pass. Combobox and diff table may be descoped to a select and a list if the pilot team lacks them; the descoping is recorded in the verification report.

### 4.5 SDK, contract and template

#### PF-8 Module SDK (complete)
Implements FR-6 in full; extends PRD-0003 SK-14.
- AC1: `slg-os-sdk-backend` adds: the service-account client for module-to-module calls (client credentials, token cache with early refresh, audience per target, retry and timeout policy, correlation id propagation); the permission cache with the 60 s bound and invalidation on 401/403 from the core; DEGRADED/UP/DOWN readiness with dependency checks; an `/info` endpoint reporting module and schema version; Micrometer metrics per NFR-8; structured JSON logging with a personal-data-free MDC; a test-support module (`slg-os-sdk-test`) that issues signed test tokens and fakes the permission API. The SDK rejects service-account tokens on user endpoints and BFF-client tokens on service endpoints (PF-11 AC1).
- AC2: `@slg-os/sdk-frontend` adds: shortcut registration with collision rejection and help integration (UI-15), shell dialog and toast APIs, a `lang` helper for mixed-language text, route integration with the shell's deep links. It still exposes no token and no raw `fetch`. The module badge API of earlier drafts is removed (notifications are deferred).
- AC3: Contract version `1.0` is kept if no manifest field is added or changed; the fields `allowedCallers` and `errorCodes` belong to schema 1.0 (if the skeleton schema lacks `allowedCallers`, it is added to 1.0 in B2a, before the first external module). Additive changes later raise the minor version; the SDK, schema, kit and template carry the same version and a CI check fails if they disagree. Breaking changes follow Q13 and need an ADR.
- AC4: Publishing: SDK artefacts go to the organisation's GitHub Packages (Maven and npm) from a release workflow that runs in a protected environment with required reviewers, from protected tags, attaching an SBOM and the version in `CHANGELOG.md`. Provenance (npm provenance, signatures) is used if the plan supports it for private repositories; otherwise ADR-0019 records the alternative (checksums plus an SBOM attestation by other means). Consumer CI verifies signatures or provenance where they exist and pins exact versions; no personal access tokens with package read scope outside the package access grants (Q43). Renovate or Dependabot configuration ships in the template.
- AC5: Backward compatibility within a contract major: a test builds the previous SDK release's reference module against the new SDK and passes; the OpenAPI diff gate of PRD-0003 covers the core and SDK-facing APIs.

#### PF-9 Contract test kit and checklist automation
Implements FR-7 AC1, module registration checklist.
- AC1: A package `slg-os-contract-tests` (Java and a CLI `slg-os-check`) verifies: manifest schema and semantic rules (permission names, error-code keys in both languages, `requires` ranges, entry points, string normalisation of PF-5 AC8), build layout (`build-manifest.json`, file types, no HTML, no secrets in source maps), i18n key parity and placeholders, health and readiness endpoints, token validation against forged tokens (wrong audience, wrong `azp`, expired, bad signature), 403 without permission on every annotated endpoint, remote loading in the shell fixture (mount, theme and language switch, error boundary), render-count stability, the lint rules of UI-21, and the version of the template the module was created from (a warning when more than one minor behind).
- AC2: The kit prints human-readable text and JSON with stable check ids, severity and remediation link, exits non-zero on failure; messages are English. `docs/reviews/module-registration-checklist.md` marks which items the kit checks (with the check id) and which need human review; the report link is recorded in the activation step. Manual items stay manual (internal repository, owner team, PRD, four-eyes review recorded).
- AC3: The kit has golden valid and invalid modules; each check fails on a deliberately broken module (negative tests). The golden invalid module includes a missing German key and the message names file and key. The outdated checklist item about a manifest hash is rewritten (C17).

#### PF-10 Module template
Implements FR-7.
- AC1: A GitHub template repository (`slg-os-module-template`) is generated from `templates/module` of this monorepo by a sync workflow on release (the monorepo stays the source; the sync uses a deploy key scoped to that one repository; a drift check runs on both sides). It contains: Spring Boot backend wired to the SDK (auth, permissions, i18n resources, logging, health, Flyway), Vite/React remote wired to the frontend SDK with the settings of FR-7 AC2, Dockerfile (multi-stage, non-root, read-only root file system, limits from NFR-7), compose snippet with the secret mounts of PF-4, manifest, i18n skeleton (de, en), CI workflow (build, tests with the 80 % gates, the kit, dependency and image scanning, SBOM, image signing, digest output, manifest validation), `@slg-os/eslint-config`, `CODEOWNERS`, PR template with the registration checklist, an English `README`.
- AC2: Core CI generates a module from the template at the current version, builds it from a clean checkout, runs its tests with coverage, registers it on the E2E stack, signs in as a permitted user and asserts that its window opens, a permission denial works and the kit passes (FR-7 AC1).
- AC3: The kit compares the module's gate configuration with the template's (NFR-2) and reports differences.
- AC4: Developer documentation (English, `docs/developers/`): getting started, contract reference (generated), error-code convention, permission naming, i18n rules, local development against a compose dev profile (hot reload of a remote inside the shell, not verified by the spike, is verified here or its limits stated), upgrade and rollback, troubleshooting.
- AC5: Effort measurement: a developer new to the platform builds a module with one window and one protected endpoint following only the documentation; start and end time, the stumbling points and the first failing message seen are recorded. Target under one working day. The protocol (participant criteria, task script) must be fixed before the phase closes; the result is recorded when available and a miss opens a defect list, but it never blocks a merge.

#### PF-11 Module-to-module calls
Implements 8.4.
- AC1: A manifest entry point lists `allowedCallers`. The provisioner grants a caller's service account the target audience only if the target lists the caller; removal takes effect at the next activation. The target validates: `aud` contains itself, `azp` is the service-account client of a registered module (never the BFF client), `sub` is that service account, and it looks up `allowedCallers` itself rather than trusting the token alone. Service tokens live at most 5 minutes; a service token on a user endpoint and a forwarded user token on a service endpoint are both rejected.
- AC2: A second reference module (`reference-consumer`, in the monorepo, built from the template) calls the reference module's notes API through the SDK client. Tests: an allowed call succeeds; a module not listed gets no audience; the two token kinds cannot be replayed across endpoint kinds; a user id passed in a header is ignored for authorisation.
- AC3: Module-to-module calls do not pass the gateway; metrics and logs carry caller and target module ids; calls to a DOWN module fail within the SDK timeout with a mapped error.

### 4.6 Operations

#### PF-12 Alerts, jobs and operational overview
Implements NFR-8, NFR-9, FR-10, Q30 (in-product alerts only).
- AC1: Job framework (built in B1): jobs take `pg_try_advisory_lock` on a dedicated, non-pooled connection held for the run; `job_run` rows carry a heartbeat and are marked `abandoned` after three missed heartbeats; an overrunning job is skipped, not stacked; start jitter; last run and result are metrics (tag `job`) and one log line per run. Test: kill the container mid-job; a second container takes over.
- AC2: Alerts are persisted (`alert`: kind, subject, severity, first seen, last seen, state `open|acknowledged|resolved`, count) with de-duplication per kind and subject. The `subject` is a closed enumeration or a module id; details live only in the audit entry; no IP, user name or free text is stored in an alert (test over the table). They are shown in the Overview and as an administrator-only tray indicator (not the notification centre). Acknowledging is audited; an alert resolves itself when the condition clears; resolved alerts stay visible for 7 days.
- AC3: Detector table (data source, credential, test stub):

| Kind | Source | Credential |
|---|---|---|
| AD/LDAP unreachable | Keycloak LDAP connection test through the admin API, every 5 minutes; if Keycloak needs a broader right than can be limited, the detector uses failed-login reason codes and ADR-0021 records the choice | a dedicated health service account |
| break-glass or unknown master login, `login-audit-gap` | PF-2 | audit readers |
| certificate expiry < 30 days (both host names) | TLS handshake with SNI to the configured proxy address, reading notAfter | none |
| backup failed or older than 36 hours | signed status record (PF-15 AC3) | read-only status volume |
| module DOWN > 5 minutes | health poller | none |
| store >= 70 %, store verification, audit chain failure | PF-5, PF-1 | none |
| credential rotation due | PF-4 | none |
| clock drift > 60 s | compare with a configured NTP source or the host time status exposed read-only on the status volume; without a source the detector reports "unknown" and the limitation is documented | none |
| session store or Keycloak degraded | existing health state | none |

- AC4: Every kind has a test that creates the condition (stubs, fake clock), observes one alert, de-duplication, clearing and resolution. Alerts are also logged with a stable `alertKind` at `WARN` or `ERROR`. The Overview works when Keycloak, the store or a module is down; a failing detector reports "unknown" with its reason code.
- AC5: Until Q30 is decided nobody is notified outside the platform; the operator documentation states this first in the monitoring chapter (doc check).

#### PF-13 Operational runbooks and recovery
Implements FR-5a AC3, NFR-5.
- AC1: Runbooks (German and English, `docs/operations/`): first start with bootstrap admin, lock-out recovery, break-glass use, certificate renewal for both host names, credential rotation, module upgrade and rollback, store and audit verification failures, restore from backup, Keycloak or LDAP outage. Each names the alert that triggers it.
- AC2: Lock-out recovery and break-glass are exercised in an E2E test: recovery restores an admin; a break-glass login produces the alert and the audit entry within two poll intervals (60 s).
- AC3: Core upgrade and rollback are tested on the compose stack (NFR-5): upgrade with migrations from the previous release, a request flow, rollback to the previous image (expand-only migrations), a request flow.

#### PF-14 Privacy tooling
Implements 8.9.
- AC1: An administrator (`platform.privacy.manage`, step-up) can, for a user id: export the user's stored preferences, layout and the audit entries naming the user as actor or object (JSON and CSV through the shared writer), and delete the user's preferences and layouts (a POST with the user id in the body, confirmed by retyping the id). Other persons named in exported audit entries (actor or object) are redacted to pseudonymous ids. The page shows the data categories and counts, states that audit entries are not deleted, offers the export first, and reports what was removed. Export file names contain no personal data. The export covers everything holding the user id (sessions, alerts, activation actor, job records); module-owned data is out of scope and said so. Each use is audited and alerts the other administrators.
- AC2: Preferences and layouts of users no longer in the directory are removed 90 days after disappearance. A daily job compares stored user ids with the Keycloak user list; it aborts and alerts when the list is empty, smaller than 50 % of the previous count, or the federation test failed, and it deletes at most 10 % of stored users per run. Test with a fake clock and a failing listing.
- AC3: The Art. 30 record input is generated as a table from column annotations (every column holding personal data, including JSON and free-text columns, carries an annotation) into `docs/operations/privacy-record.md`; a CI check fails when an annotated column lacks an entry. The limits of the check (unannotated columns) and the erasure limit (backups keep deleted preferences for up to 14 daily and 8 weekly copies) are stated in the file.

#### PF-15 Backup completion
Implements NFR-5; extends PRD-0003 SK-17.
- AC1: A backup container runs the skeleton's script nightly (time configurable) and on demand. It backs up the platform database, the Keycloak database, every module schema listed by the registry, the globals (roles, with passwords re-applied from secrets), the realm export, the store volume; session data is excluded. It uses the read-only `slg_backup` role.
- AC2: The target is a directory inside the container. The operator mounts the SMB share as a Compose volume with `cifs` options; the credentials come from a host credentials file (mode 0600) referenced in the options, because volume options are not secret-aware, and the documentation says docker-group members can see the options. A sentinel file is checked before and after each run, so an unmounted share (which Docker would silently replace with an empty local directory) fails the run. Output is `age`-encrypted for a public key configured on the host; the private key is held offline by the operator. Retention 14 daily and 8 weekly copies is enforced on the target.
- AC3: Each run writes an atomically replaced status record (run id, time, result, sizes, audit head hash and seq, store tree hashes per module, HMAC under a key shared read-only with the core) on a volume the core mounts read-only; a record older than 36 hours, from the future or with a bad HMAC is the backup alert. The record contains no credentials.
- AC4: Restore test (nightly and on changes under `deploy/backup/`, not on every pull request): a backup with two modules is restored into a clean stack; the test asserts registry and mappings present, store hashes match, module data present, roles and credential files still match, module service-account tokens obtained after the restore are accepted, the audit chain verifies from the checkpoint, sessions are invalid. The restore rehearsal on a clean host stays a go-live gate (phase 1c).

## 8. Security considerations
- Admin plane: all admin endpoints deny by default, check the permission server-side and require CSRF and Origin (PRD-0003 SK-4). Step-up is a re-authentication (`prompt=login`, `max_age=0`) whose `auth_time` is verified from the token stored in the server-side session, not from client input; it is valid for 5 minutes and **single-use per action class** (module activation, rollback and registration; credential rotation; purge; mapping and role changes; session revocation; audit export; privacy actions). Mass assignment is prevented by explicit request DTOs.
- Compensating controls for the single bundled admin role: `purge-data` additionally requires typing the module id and runs after a cancellable 24-hour delay with an alert; audit export, privacy export and privacy delete alert all other administrators; "revoke all" and mapping changes are audited with before and after.
- Stolen admin session: a fresh step-up is needed for sensitive actions; the 10 h absolute session and the 5-minute step-up bound the window. A compromised administrator can still register a malicious module: that risk is accepted through ADR-0007 and the process-based review of Q38, and stated here so the owner knows the tool does not enforce a second person.
- Provisioner: separate container with its own database role and Keycloak account restricted to `mod-*` clients (PF-4 AC2, AC3); credentials are generated with a CSPRNG, shown to nobody, delivered as files and never logged; rotated at least yearly with an alert.
- Audit: append-only grants; hash chain; signed checkpoints; fail-closed same-transaction writes; daily whole-range verification; reads audited; neutralised CSV; usernames of failed logins not stored; truncated IPs for failed logins. Audit rows hold pseudonymous ids and IPs (personal data); access requires `platform.audit.read`.
- Archive handling: zip-slip, links, bombs, collisions, nested and prepended data (PF-5 AC1); the shell never renders module-supplied HTML or SVG; manifest strings are text, normalised and bidi-safe.
- Module-to-module: rules of PF-11 AC1; service tokens 5 minutes.
- Supply chain: SDK and template artefacts follow PF-8 AC4 (protected release environment, provenance or recorded alternative, consumer verification); template sync uses a single-repository deploy key; module images are signed and referenced by digest.
- Alerts and logs: closed-enumeration subjects, no secrets, tokens, IPs or user names.
- Backups: `age` private key offline; signed status record; `cifs` options visible to docker-group members (documented).
- Data protection: new personal data are audit rows (pseudonymous ids, IPs), the privacy tooling and Keycloak's own event store. Retention: audit 6 months (whole months), Keycloak events 7 days, preferences 90 days after the user disappears, sessions as in the skeleton. DPO input on login-event ingestion, the audit viewer and export, and the privacy tooling is requested before ingestion is enabled anywhere shared (Q42, Q23).

## 9. Testing strategy
- Backend: JUnit/AssertJ/Mockito with Testcontainers (PostgreSQL with partitions and roles, Keycloak with the committed realm, events and fine-grained permissions, LDAP stub); concurrency tests for the chain (threads and two containers); property-style tests for the canonical encoding; archive fuzz corpus; ArchUnit rules (the provisioning client is the only caller of the provisioner API; one shared CSV writer; no admin controller bypasses the permission annotation, plus the reflective endpoint enumeration of PF-6 AC6).
- Frontend: Vitest + Testing Library + MSW for admin pages; Playwright for the main admin flows (register and activate a module, rollback with orphaned permissions, role and mapping edit, effective permissions, revoke sessions, audit viewer and export, alert lifecycle, privacy export, step-up inside a window); keyboard-only tests assert focus order, focus return and live-region text; sort and format tests run in de and en with an umlaut case; axe on every page.
- E2E on the compose stack: provisioning with credential delivery and canary scan, rotation, module-to-module call with `reference-consumer`, break-glass and lock-out recovery, backup and restore with two modules, store tampering detection, event ingestion with replay, a template-generated module registered and opened, core upgrade and rollback.
- Contract kit and template: golden valid and invalid modules, negative tests, drift check, SDK backward-compatibility build.
- CI budget: the PR gate stays at or below 25 minutes (Chromium only, one axe mode per page in light and dark, 100,000-row tests); the nightly workflow runs Firefox and WebKit, forced-colors and narrow axe modes, the 1,000,000-row migration and verification, the restore test, template drift, mutation checks and the performance measurements. Nightly failures open an issue and block release tags, not pull requests. `gate` names its required jobs.
- Time-dependent behaviour (alerts, rotation, retention, polls) uses an injectable clock. Mutation check on `audit`, `provisioning`, `store`, `security` in each milestone review.
- Coverage: gates as in NFR-P1; tests assert behaviour including failure paths; every fixed defect gets a regression test.
- Manual and external: effort measurement (PF-10 AC5), DPO review (Q23, Q42), the SMB target against the real share (Q9), real-AD group listing (Q41).

Resolutions where reviews differed or the author chose:
- Audit durability: the security review wanted fail-closed writes in the business transaction; operations wanted the lock held only briefly. Both applied: the audit insert is in the same transaction and the head lock is the last statement before commit (PF-1 AC3).
- Provisioner isolation: security asked for a separate container; operations showed that a shared volume written by the core exposes all secrets. Applied together with the two-role rotation (PF-4 AC2, AC5); the Q39 spike still decides the delivery path.
- Admin split: security asked for separate roles or compensating controls; the owner's earlier decision (one role, process-based review) stands, so compensating controls were added (section 8) and the permission split is declared a naming unit, not a boundary.
- Q45: security recommended a default of an external anchor; the author kept "no" but put the head hash into the signed backup status record and the target's history, which gives most of the value at no extra component.
- Effort measurement: operations and requirements reviews agreed it cannot be a merge gate; the protocol must exist, the result is recorded when available.
- Alerts versus UI-11: the requirements review noted the tray indicator conflicts with the deferred notification centre; the indicator is administrator-only and fed by `alert`, the module notification API is removed.
- "Last time an administrator looked at the overview" (earlier draft) was dropped as personal-data tracking without purpose.
